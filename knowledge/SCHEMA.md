# Knowledge Base Schema & Operation Guidelines (LLM-Wiki x OKF)

> このプロジェクト固有の取り入れ方は [`OKF.md`](./OKF.md) を参照。
> 本書は知識ベース（`wiki/`）の構造・編集規約（憲法）を定義する。

## 1. 概要
このリポジトリの知識ベースは、静的フォーマット標準「OKF (Open Knowledge Format) v0.1」と、AIエージェントによる動的知識管理アプローチ「LLM-Wiki」を統合して構成されています。
あなた（Claude Code）は、以下のルールとディレクトリ構造に従って既存のファイルを「コンパイル（編集・統合）」し、構造化された生きた知識を自律的に維持・成長させてください。

## 2. 想定するディレクトリ構造と役割
ナレッジベースは以下のツリー構造（3層+1層アーキテクチャ）で管理します。あなたは主に `wiki/` 層を重点的に自律更新します。

```text
project_root/
├── input/                # 【第1層 / 揮発】raw の投入口 ※gitignore・Wiki 化したら使い捨て
│
├── knowledge/
│   ├── ref/              # 【第1層 / 保持】不変のソース (Source of Truth) ※gitignore
│   │   └── doc/          #   Wiki 作成後も原本参照が必要なドキュメント（要件定義原本・議事録・DB定義など）
│   │
│   ├── wiki/             # 【第2層】LLM所有のMarkdown群 (OKF準拠)
│   │   ├── index.md      # 予約ファイル: wiki全体の目次（フロントマターなし）
│   │   ├── log.md        # 予約ファイル: 変更履歴（ISO 8601日付で見出し化）
│   │   ├── requirements/ # 要件・仕様（このプロジェクトの主対象）
│   │   ├── architecture/ # システム構成・技術選定（このプロジェクトの主対象）
│   │   ├── db/           # テーブル定義（このプロジェクトの主対象）
│   │   ├── screens/      # 画面仕様
│   │   ├── concepts/     # 概念・用語の定義
│   │   ├── entities/     # 組織・人物・システムなどの実体
│   │   ├── synthesis/    # 複数の情報を統合・分析したレポート
│   │   ├── _assets/      # 要約不能な一次資産（構成図・スキーマ定義等。Git 追跡対象）
│   │   └── graph/        # 【オプション第4層】関係性データ (nodes.jsonl)
│   │
│   ├── SCHEMA.md         # 【第3層】Wikiの憲法 (このファイル自身)
│   └── OKF.md            # このプロジェクトでの取り入れ方
│
└── output/               # 生成物置き場 ※gitignore・Wiki 化したら使い捨て
```

### 各層の定義
1. **第1層 (ソース)**: **`input/`（揮発）と `knowledge/ref/`（保持）に分かれます。**
   - `input/` は受領資料・議事録・要求文書の**投入口**です。Wiki へ整理され次第、使い捨て可能です。`output/`（生成物）も同様に扱います。
   - `knowledge/ref/doc/` は、**Wiki を作成した後も原本参照が必要なドキュメントを恒久保持**する場所です。一度投入されたら変更しません（更新は世代を分けた別ファイルとして追加）。どちらも Git では追跡しません（gitignore）。役割分担の詳細と判断基準は [`OKF.md`](./OKF.md) §1.1。
2. **`wiki/` 層 (LLM所有のMarkdown)**:
   あなたが自律的に更新・管理するOKF準拠のMarkdown群です。主に `screens/`, `db/`, `entities/`, `concepts/`, `synthesis/` ディレクトリに整理してください。
3. **`SCHEMA.md` (このファイル)**:
   Wikiのルール定義です。あなたは常にこのスキーマに従って編集を行います。
4. **`wiki/graph/` (オプションのグラフ層)**:
   ベクトル検索では難しいリレーショナルなクエリに対応するため、フロントマターから抽出された関係性を保持するディレクトリです。

## 3. ファイル・フォーマット仕様 (OKF準拠)
`wiki/` 配下に作成・更新するすべてのMarkdownファイルは、以下のOKF仕様に従う必要があります。

### 3.1 1コンセプト = 1ファイル
1つの概念につき1つのMarkdownファイルを作成してください。ファイルパス自体がそのコンセプトの「ID」として機能します。

### 3.2 YAMLフロントマターの必須化
非予約のMarkdownファイル冒頭には、必ず解析可能なYAMLフロントマターを記述してください。
**`type` フィールドは必須**です。
```yaml
---
type: concept  # 必須 (例: concept, entity, screen, table, synthesis 等)
title: コンセプトのタイトル # 推奨
description: 概要 # 推奨
tags: [tag1, tag2] # 推奨
timestamp: 2026-06-22T00:00:00Z # 推奨 (ISO 8601形式の更新日時)
---
```

### 3.3 予約ファイル
以下のファイル名は特別な役割を持つため、指定の構造に従ってください。
- **`index.md`**: ディレクトリ内の内容を列挙する段階的開示用ファイルです。このファイルにはYAMLフロントマターを持たせません。
- **`log.md`**: 変更履歴です。ISO 8601形式の日付を見出しとしてグループ化してください。

### 3.4 相互リンクとグラフ構造
本文は自由ですが、コンセプト間の関連性は通常のMarkdownリンクを用いて相互参照させてください。
※ ビジュアライザー等の互換性のため、リンクは絶対パスではなく**相対パス（例: `[顧客情報](../entities/customers.md)`）**を使用してください。

## 4. 運用・編集ルール (LLM-Wikiアプローチ)
- **知識のコンパイル:** 新しい情報（`input/` への投入など）が入るたびに、毎回断片的に検索して答えるのではなく、既存のMarkdownファイルを読み込み、情報を統合・矛盾を解消してナレッジをアップデートしてください。整理が済んだら、保持が必要な原本を `knowledge/ref/doc/` にコピーします（[`OKF.md`](./OKF.md) §1.1）。
- **外科的編集 (`str_replace`の活用):** トークンの節約とGit差分の可読性を保つため、ファイル全体を書き換えるのではなく、特定の行だけを外科的に置換・編集してください。
- **ページサイズ制限 (Atomic pages):** コンテキストウィンドウを使い果たさないよう、1ファイルの行数は400〜800行程度を上限の目安とし、肥大化した場合はファイルを適切に分割（Sharding）してください。
