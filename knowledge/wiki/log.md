## 2026-08-26

### 監査列（`createdAt` / `updatedAt` / `createdById` / `updatedById`）の要否を運用面から再検討し、追加した

- 契機は「**手動でデータを更新して運用で回す箇所があれば列が要るはず**」という指摘。全10テーブルを、**行が更新されるか**と**更新の主体が人か**の2軸で見直した。
- **人手が入る箇所は3つ**だった。F-7-1 のスタッフ管理（登録・編集・無効化）、F-5-1 の会員編集と F-8-5 の CSV インポート、F-4-5 の申請項目編集。このうち**申請だけは既に `processedById` / `lastEditedById` で追える**が、**スタッフと会員は誰がいつ変更したかを残す手段が無かった。**
- とくに `StaffUser` は、**`role` の `staff → admin` 昇格と `isActive` の無効化が権限そのものの変更**でありながら履歴テーブルを持たず、しかも **F-9 のリセットで削除されない**（F-9-5）ため商談を跨いで蓄積する。ここを最優先とした。
- `Member` は `status` の変更だけが `StatusHistory` に残り、**住所・電話・氏名の修正はどこにも残らない**状態だった。表記ゆれ対応で氏名を直す動線（F-5-5・F-6）があるため実害になる。
- `MatchCandidate` は**再実施で既存行の `ruleScore` / `aiLikelihood` を更新する**設計（`UNIQUE(applicationId, memberId)` の項）でありながら、生成時刻も更新時刻も持っていなかった。
- `Member` の作成時刻は既存の `registeredAt` を改名して充てた（下記の列名統一）。**当初は「登録日は CSV インポートで過去日付が入り得るので作成時刻とは別概念」として2列を持たせたが、これは誤りだった**（次項）。

**一律には付けない**と決めた。付けない側の根拠:

- **追記専用のテーブルに `updatedAt` / `updatedById` を付けない**（`CheckRun` `AppStatusHistory` `StatusHistory`）。付けると「更新してよい行」という誤ったシグナルになる。`CheckRun` を実行ごとの履歴に分離したのは判定履歴を失わないためであり（判断記録 #6）、書き換える運用が存在しない。
- **同義の列を名前違いで増やさない。** `Application` の作成者・最終更新者は既存の列が該当するため、新しい列は足さない（後述の列名統一で `createdById` / `updatedById` へ**改名**した）。別名のまま新設すると、実装のたびにどちらが正かを判断させることになる。
- **`UsageCounter` に主体が存在しない**（加算するのはAI呼び出し経路）。業務データを保持させない規約にも反する。
- **`Tenant` に actor 列を付けない。** 改称するのは JV-IT の運用者で `StaffUser` として存在せず、FK を張れない値だけが入る列になる。

**`NULL` の意味を1つに固定した**: `createdById` / `updatedById` の `NULL` は「**アプリケーションを経由しない操作**」（シード投入 OP-7・OP-10、`wrangler d1 execute` による直接SQL）を表し、記録漏れを表さない。**実装未着手の今なら既存行のバックフィルが発生しないため、この意味を最初から保てる。** 後から足すと既存行が一律 `NULL` になり、この定義が壊れる。

`updatedAt` は SQLite / D1 に `ON UPDATE` が無いため**アプリケーションが必ず設定する**（Drizzle の `$onUpdate`）。作成時は `createdAt` と同値を入れ、`NULL` にしない。

> **更新の記録のみを扱う。閲覧の記録（誰がどの個人情報を見たか）は依然として無い。** これは MVP の欠落ではなく本番化の論点として `production-gap.md` に整理済みであり、今回その位置づけは変えていない。

### 同一の役割に別名が付いていた列を統一した

- 「**似たような役割が複数テーブルで異なるカラム名になっている**」という指摘を受けて全列を洗い直した。**同義の別名が6つ**あった。監査列の検討で「既存の列が担うから足さない」と判断した箇所は、裏返せば**同じ役割に別名が付いている状態を追認していた。**
- 判断の根拠は既にあった。**確定事項ではなく判断記録 #11**（`orgId` → `tenantId` の名称統一）の理由「**同一概念を2つの名前で呼ばない**」がそのまま列名にも当てはまる。新しい原則を持ち出したわけではない。

| テーブル | 原本 §9 | 変更後 | 同義である理由 |
|---|---|---|---|
| Application | `processedById` | `createdById` | 読取を実行した職員 = 行を作った職員。申請は読取以外の経路で作られない |
| Application | `lastEditedById` | `updatedById` | 「最終編集者」は最終更新者そのもの |
| CheckRun | `executedAt` | `createdAt` | 追記専用であり実行時刻と行の作成時刻が常に一致する |
| CheckRun | `executedById` | `createdById` | 実行者 = 行を作った職員 |
| AppStatusHistory | `changedById` | `createdById` | 追記専用であり変更者 = 行を作った職員 |
| StatusHistory | `changedById` | `createdById` | 同上 |
| Member | `registeredAt` | `createdAt` | 登録日は行が作られた時刻そのもの（下記） |

- 規約として **「その行にとって何が起きたかを列名に持たせない」** と定めた。読取なのかAI実行なのかステータス変更なのかは**テーブルが表している**（`Application` / `CheckRun` / `AppStatusHistory`）ため、列名で重ねて言わない。
- **改名しない列**も明示した。`MatchCandidate.decidedById` / `decidedAt`（**作成でも一般の更新でもない第3の事象**。`ruleScore` 更新時の `updatedAt` とは別に動く）、`Session.expiresAt` / `staffUserId`、`StaffUser.lockedUntil`、`UsageCounter.period`。
- **監査列の NULL 可否に例外を設けた。** 既定は NULL 可だが、**アプリ外で行が作られ得ないテーブルは NOT NULL に強める**（`Application` `CheckRun` `AppStatusHistory` `StatusHistory`）。シード投入の対象は職員2件・会員5件だけであり（OP-7）、これらのテーブルに行を作る経路は画面しかない。改名前の `processedById`（NOT NULL）の強さを落とさないための整理でもある。
- **列の並び順も規約にした。** 監査列はテーブル末尾に `createdAt` → `updatedAt` → `createdById` → `updatedById` の順で置き、業務上の列と混ぜない。
- DTO（[types.md](./architecture/types.md)）の `processedBy` / `lastEditedBy` / `executedBy` / `changedBy` / `executedAt` も同じ規約で揃え、`api.md` の申請一覧のフィルタ名 `processedById` を `createdById` に変更した。**画面に出す日本語ラベル（「処理者」「変更者」）は変更していない** — 列名は実装の語彙、ラベルは利用者の語彙であり、揃える対象ではない。
- **判断記録 #7**（`AppStatusHistory.changedById` / `Application.lastEditedBy` をリレーション化）は**行を書き換えず**、表の下に改名の注記を付けた。要求ドキュメントとの差分の記録であり、リレーション化したという判断内容自体は変わっていないため。

#### `Member.registeredAt` を「別概念」とした判断を撤回した

- 統一の検討時、`registeredAt` は **F-5-2 の業務項目「登録日」であり CSV インポートで過去日付が入り得るから作成時刻とは別概念**だとして改名対象から外し、`createdAt` を別に新設した。**この根拠は要件に裏付けが無く、誤りだった。**
- 「レコードが登録されるタイミングで決まるのでは」という指摘を受けて確認した結果:
  - `CreateMemberRequest`（[types.md](./architecture/types.md)）は**登録日を受け取らない。** サーバーが設定する。
  - **CSV インポートの列定義はどこにも存在しない。** F-8-9 が「エクスポートはインポートと同一形式」と定めるだけで、登録日を読み込むとはどこにも書かれていない。過去日付が入る経路は**要件上存在しない。**
  - F-9 の[シード会員の値を復元しない根拠](./requirements/functional.md#シード会員の値を復元しない根拠)にある「いずれの操作でも変化しない」も、作成時に一度だけ設定されることと整合する。
- したがって `registeredAt` と `createdAt` は**同じ値の別名**であり、まさに今回是正した問題そのものだった。`registeredAt` を `createdAt` へ改名して1列に統合し、`Member.createdAt` の新設は取り消した。
- **F-5-2 の保持項目「登録日」は失われていない。** 保持先が変わっただけであり、画面ラベルは「登録日」のまま。データモデルに**画面ラベルと列の対応表**を追加した（処理者 / 変更者 / 登録日）。
- 教訓: 「別概念だから別列」と言うときは、**その2つが食い違う具体的な経路を要件から示せなければならない。** 示せないなら別名である。

#### `MatchCandidate.decidedById` は残す（食い違う経路を確認した）

- 同じ問い（「最終更新者＝決定した人では」）を `decidedById` にも当てた。こちらは**食い違う経路が要件から出た**ため残す。
- 行への書き込み経路が2つあり、順番が入れ替わる。**職員Xが「保留」と判断**（F-6-8）した後に**職員Yが業務チェックを再実施**（F-4-6）すると、既存行の `ruleScore` / `aiLikelihood` が更新され、**最終更新者はY・判断者はX**になる。「保留」は再実施して再判断するための状態であり、この順番は想定された動線である。
- 加えて **F-6-9 が「判断結果・判断者・日時を保存する」と明示**しており、監査の付帯情報ではなく要件が名指しする業務データである。`decidedById` の `NULL` が `status = pending` と一対一で対応する点も、`updatedById` の `NULL`（一度も更新されていない）とは両立しない。
- 一方 **`MatchCandidate` に `updatedById` は置かない。** 再実施の実行者は `CheckRun.createdById` に残るため重複する。ただし `MatchCandidate` から `CheckRun` への参照が無く、**単体では「最後に誰が再算出したか」を引けない**ことはページに明記した。

- **NF-2-35〜41 を新設。** 上限値の型・範囲検証（1以上の整数、それ以外は起動失敗）、コードへのハードコード禁止（変更は環境変数＋再デプロイのみで完結し、スキーマ変更・コード修正・データ移行を要しない）、引き下げ時の遡及適用、リクエスト単位の上書き手段を設けない、条件付き UPDATE による原子的な予約、F-9 でカウンタを初期化しない、テナント横断のグローバル保持。
- **`UsageCounter` は `tenantId` を持たない唯一のテーブル**とした。Document AIの無料枠がGoogle Cloudプロジェクト単位のため、テナント別に分割すると総量を抑えられない（NF-2-41）。全クエリへの `tenantId` 付与規約の対象外となるため、業務データを保持させない制約を付けた。
- **累計→月次へ変更した理由**: Document AIの無料枠（月1,000ページ）が月単位であり、保護対象と判定単位を一致させる必要がある。旧方式（累計50枚＋F-9 でリセット）はリセットを繰り返すことで月内に無料枠を超過し得た。
- **同時実行の限界を解消**: 旧 NF-2-19 の注記にあった「同時リクエストが上限付近で競合すると数件超過し得る」は、条件付き UPDATE（`WHERE period = ? AND count < ?`）で影響行数 0 を上限到達とする方式により発生しなくなった。代わりに**加算をAI呼び出しの前に行うため、失敗した試行も枠を消費する**（fail closed 側に倒す判断）。
- 反映先: `requirements/non-functional.md`、`requirements/acceptance.md`、`requirements/decisions.md`（確定事項 #10）、`requirements/functional.md`（F-2 注記・F-9-5・F-9-9）、`db/data-model.md`（`UsageCounter` 追加・`Application` 注記）、`screens/screen-list.md`、`architecture/ai-api.md`、`architecture/index.md`。
