### 実装領域（`docs/dev/`）との境界を確定し、`index.md` に導線を追加

- tsumiki（`dev-*` スキル）の導入にあたり、**要件定義のやり直しは行わない**と判断した。要件は v1.10 で確定済み（未確定事項なし）で、`dev-plan` の Full-spec モードが生成する EARS 要件・ユーザーストーリー・受入基準は、本 Wiki の `functional.md` `overview.md` `acceptance.md` と重複する。再生成すると正典が二重化し、**`decisions.md` の「撤回した判断」のように再生成では復元されない情報が落ちる**。
- tsumiki の出力先 `docs/dev/` は Wiki 配下へ移さない（シンボリックリンク案を棄却）。理由は2点。
  1. tsumiki のタスクファイルのフロントマターは `id / status / priority / dependencies` で **`type` を持たず**、[SCHEMA.md](../SCHEMA.md) §3.2 に違反する。ツールの出力に合わせて憲法を緩めることになる。
  2. `docs/dev/context.md` から Wiki への相対リンク（`../../knowledge/wiki/...`）は、実体が Wiki 配下にあると解決先がずれて壊れる。**GitHub の Web UI はシンボリックリンクを辿らない**ため、「Wiki 側から一箇所で読める」という目的と逆の結果になる。
- 代わりに**境界を寿命で引く**方針を明文化した。Wiki は要件が変わるまで変わらない長寿命の知識、`docs/dev/` は実装が進むたび書き換わる作業状態（タスクの `status`、`dev-verify` のレポート）。`docs/dev/` 配下は §3.2 の適用外とする。

- **画面仕様書だけは例外**として、`dev-screen-spec` が `docs/dev/screen-specs/` に生成した後、`knowledge/wiki/screens/`（[SCHEMA.md](../SCHEMA.md) §2 で画面仕様の主対象と定められている）へ正典化する運用とした。画面仕様は長寿命の設計情報であり、作業状態ではないため。

### AI呼び出し上限を累計から月次へ変更し、専用カウンタテーブルを新設

- **NF-2-18 を「累計の読取枚数」から「月間の読取枚数」へ変更。** 環境変数を `MAX_OCR_PAGES` → **`MAX_OCR_PAGES_PER_MONTH`（120）** へ改名した。意味が変わる設定値を同名で流用すると既存環境・ドキュメントとの間で誤解が生じるため。
- **NF-2-34 を新設。** 月間のGemini呼び出し上限 `MAX_GEMINI_CALLS_PER_MONTH`（720）。Pass①・Pass②を合算し、NF-2-17 を月次カウンタで満たす。
- **NF-2-19 を反転。** 旧「専用のカウンタテーブルは設けない／`Application` の件数で判定」を撤回し、**専用テーブル `UsageCounter` を新設**した。期間キー `YYYY-MM`（JST）を PK とし、保存済みの期間キーが現在と不一致なら 0 として上書きする（日付判定による明示的リセット処理を持たない＝月初にアクセスが無くても取りこぼさない）。
- **NF-2-20 を変更。** 上限到達時の案内を「admin によるリセット（F-9）が必要」から「翌月まで待つか上限値の引き上げ（再デプロイ）が必要」へ。**F-9 では解除されない**旨を明記。
- **NF-2-35〜41 を新設。** 上限値の型・範囲検証（1以上の整数、それ以外は起動失敗）、コードへのハードコード禁止（変更は環境変数＋再デプロイのみで完結し、スキーマ変更・コード修正・データ移行を要しない）、引き下げ時の遡及適用、リクエスト単位の上書き手段を設けない、条件付き UPDATE による原子的な予約、F-9 でカウンタを初期化しない、テナント横断のグローバル保持。
- **`UsageCounter` は `tenantId` を持たない唯一のテーブル**とした。Document AIの無料枠がGoogle Cloudプロジェクト単位のため、テナント別に分割すると総量を抑えられない（NF-2-41）。全クエリへの `tenantId` 付与規約の対象外となるため、業務データを保持させない制約を付けた。
- **累計→月次へ変更した理由**: Document AIの無料枠（月1,000ページ）が月単位であり、保護対象と判定単位を一致させる必要がある。旧方式（累計50枚＋F-9 でリセット）はリセットを繰り返すことで月内に無料枠を超過し得た。
- **同時実行の限界を解消**: 旧 NF-2-19 の注記にあった「同時リクエストが上限付近で競合すると数件超過し得る」は、条件付き UPDATE（`WHERE period = ? AND count < ?`）で影響行数 0 を上限到達とする方式により発生しなくなった。代わりに**加算をAI呼び出しの前に行うため、失敗した試行も枠を消費する**（fail closed 側に倒す判断）。
- 反映先: `requirements/non-functional.md`、`requirements/acceptance.md`、`requirements/decisions.md`（確定事項 #10）、`requirements/functional.md`（F-2 注記・F-9-5・F-9-9）、`db/data-model.md`（`UsageCounter` 追加・`Application` 注記）、`screens/screen-list.md`、`architecture/ai-api.md`、`architecture/index.md`。
