# テナント分離方針と4層防御

> 正典化元: 要件定義書 v1.5 §7.5・§9.1（原本は `knowledge/ref/doc/claude_code_要件定義_v1.5.md`）
> スキーマ上の各テーブルの `tenantId` 列は [データモデル](../db/data-model.md)。

**全クエリに `tenantId` 条件を付与する。** ここは保守性ではなく**セキュリティ要件**として扱う。他テナントのデータ露出はこのシステムにおける最も重大な障害であり、以下は「努力目標」ではなく実装必須事項である。

## 用語

本プロジェクトでは、データの帰属先となる顧客組織を一貫して**テナント**（列名 `tenantId`）と呼ぶ。要求ドキュメント §10 の `orgId` は同一の概念を指すが、**`tenantId` に統一し、`orgId` という名称は使用しない。**

`tenantId`（内部ID）と `Tenant.code`（テナントコード）は別概念である。[両者を分ける理由](../db/data-model.md#id-と-code-を分ける理由)を参照。

## 方針

**スキーマをテナント対応形とし、かつ全クエリに `tenantId` 条件を付与する。** ただし **MVP が扱うテナントは設定ファイルで固定した1件に限定する。**

| | MVP | 将来（マルチテナント化時） |
|---|---|---|
| 全テーブルの `tenantId` 列 | **実装する** | 同左 |
| `UNIQUE` / `INDEX` の複合キー化 | **実装する** | 同左 |
| R2キーへの `tenantId` プレフィックス | **実装する**（NF-5-21） | 同左 |
| INSERT 時の `tenantId` 設定 | **実装する** | 同左 |
| **SELECT / UPDATE / DELETE のテナント条件** | **実装する**（NF-5-7） | 同左 |
| `tenantId` の供給源 | 環境変数 `TENANT_ID`（NF-5-1） | セッション参照へ差し替え |
| リポジトリ層・呼び出し側のコード | — | **変更なし** |
| 第1層: 型による強制 | **実装する**（NF-5-6・7） | 同左 |
| 第2層: SQL検査 | **見送る**（NF-5-8） | **必須** |
| 第3層: クロステナントテスト | **実装する**（NF-5-10〜13） | 同左 |
| 第4層: 環境払い出しの運用 | **行わない**（NF-5-14・[運用要件](./operations.md)） | — |
| 1DBに存在するテナント数 | 1件（起動時に検証・NF-5-15） | 複数 |
| `Tenant.code`（テナントコード） | 列は用意するが**使用しない** | ログイン時のテナント指定に使用 |
| テナントの識別・切り替え・管理画面 | **実装しない**（[スコープ対象外](./overview.md#対象外実装しない)） | 実装が必要 |

## 前提: 規約では防げない

「全クエリに `WHERE tenantId = ?` を書くこと」というコーディング規約は、**必ずどこかで破られる**。新規エンドポイントの追加時、急ぎの修正時、あるいは単純な見落としで1箇所抜ければ他テナントのデータが露出する。しかも露出したことは正常系のテストでは検出されない（1テナントしか投入していないため全件が自テナントであり、条件の有無で結果が変わらない）。

したがって要件は「書くこと」ではなく、**「書き忘れても事故にならない構造にすること」**とする。以下の第1層〜第4層は独立しており、いずれか1層が破られても他が機能する。

## なぜ MVP でもクエリ条件を実装するのか

MVP はテナントが1件のみのため、クエリ条件が無くても動作は変わらず、露出するデータも存在しない。それでも初めから実装する理由は次のとおり。

**条件を後から全クエリに追加する作業は、追加漏れを検出できない。** 網羅すべきクエリの一覧は、実装が進むほど把握が困難になる。数十のリポジトリ関数に対して「1つも漏れていないこと」を後から証明する手段がない。初めから第1層（型による強制）の上に実装していれば、そもそも漏れが発生しない。

**列だけを持たせて条件を書かない状態は、将来の担当者を誤解させる。** スキーマ上は複数テナントを表現できるのにアプリケーションは1テナントしか安全に扱えない、という差は読み取れない。「DBがマルチテナント対応なのだから複数顧客を載せてよい」と判断されれば全データが相互に露出する。

一方、**テナントの識別・切り替え**は MVP に不要であり、実装しない。`tenantId` の供給源を1つの関数（NF-5-1）に閉じ込めることで、この部分だけを後から差し替えられる構成とする。

## スキーマ側を今確定させる理由

SQLite / D1 では `UNIQUE` 制約とインデックスの先頭列を後から変更するにはテーブル再作成を要する。既存データが新しい制約に違反していれば、その移行は失敗する。

ただし **MVP はテナントが1件のみであるため、複合制約を後から張り替えることも可能ではある**（重複が発生し得ないため移行は必ず成功する）。したがってこれは「今しか設定できない」ものではなく、**「今入れておくのが最も安く、後回しにする利点がない」**という判断である。

> **撤回した論拠**: 要件定義書 v1.2 までは「複数環境のデータを統合する時点で `memberNumber` が全件衝突するため今しか設定できない」と記載していた。v1.4 で顧客ごとの環境払い出しを取りやめたため、統合すべき別環境が存在しなくなり、この論拠は成立しない。複合制約自体は引き続き妥当だが、緊急性は上記のとおり下がる。

## 実装コストの見立て

クエリ条件の付与そのものは、NF-5-6 のスコープ済みハンドルを最初に用意すれば以降のリポジトリ関数で追加記述が発生しない。**MVP における追加工数の実体は、クロステナント統合テスト（NF-5-10〜13）の構築である。**

当初この方式を棄却した理由もこのテストコストであった。テストを省略すればコストはほぼ消えるが、その場合テナント条件が実際に機能しているかを一度も検証しないまま出荷することになり、条件を書いた意味が失われる。**このテストは削らない前提で方針を決めている。**

SQL検査ラッパ（第2層）は MVP では見送るため、この工数は発生しない。

## テナントIDの解決

| ID | 要件 |
|---|---|
| NF-5-1 | **`tenantId` を返す関数を1つだけ定義し、これを唯一の供給源とする。** MVP ではこの関数が環境変数 `TENANT_ID` の値を返す。マルチテナント化にあたっては**この関数の実装のみをセッション参照へ差し替え**、リポジトリ層・ハンドラ側は一切変更しない |
| NF-5-2 | **リポジトリ層およびハンドラから環境変数 `TENANT_ID` を直接参照しない。** 必ず NF-5-1 の関数を経由する。直接参照が散在すると、差し替え時に1箇所での変更という前提が崩れる |
| NF-5-3 | **リクエストのパス・クエリ文字列・ヘッダ・ボディに含まれる `tenantId` 相当の値は、いかなる場合も信用せず、受け付けもしない。** MVP・将来を問わず適用する |
| NF-5-4 | 環境変数 `TENANT_ID` は**デフォルト値を持たせず、未設定の場合は起動を失敗させる**（`PBKDF2_ITERATIONS` と同様の扱い。NF-2-5） |
| NF-5-5 | **起動時に、`TENANT_ID` に対応する行が `Tenant` テーブルに存在することを検証し、存在しなければ起動を失敗させる。** 誤ったD1データベースをバインドした状態での起動を検出する |

## ログイン画面のテナントコード入力

**MVP のログイン画面にテナントコードの入力欄は設けない。** メールアドレスとパスワードのみとする（F-1）。

理由は次のとおり。

- **MVP では入力しても意味がない。** テナントは `TENANT_ID` で1件に固定されており（NF-5-1）、入力値が一致するかを検証する以上の働きをしない
- **営業デモで摩擦になる。** 商談の冒頭、顧客の目の前でログインする場面が最初の印象を作る。そこで用途の分からないコードを打つ操作が入るのは不利になる
- **UI は後から変更できる。** スキーマの `UNIQUE` 制約と異なり、入力欄の追加はマイグレーションを伴わない。先行して作る必要がない

一方 `Tenant.code` は**スキーマ側に先行して用意する。** 列と `UNIQUE` 制約は後から追加するコストが UI より高く、かつ現時点でゼロコストであるため。

マルチテナント化の際は、この列を用いて次のいずれかでテナントを特定する。

| 方式 | 内容 | 備考 |
|---|---|---|
| ログイン画面での入力 | テナントコード欄を追加し、`Tenant.code` で解決 | 環境が1つでも成立する。MVP の構成からの移行が最も容易 |
| サブドメイン | `{code}.example.com` のホスト名から解決 | 入力操作が不要。独自ドメインの取得が前提となる（[判断記録 #9](./decisions.md)） |

## 第1層: 型でスコープ外のアクセスを不可能にする 〔MVP対象〕

| ID | 要件 |
|---|---|
| NF-5-6 | **Drizzle / D1 のハンドルをリポジトリ層の外へ export しない。** 公開するのは `forTenant(tenantId)` が返すスコープ済みハンドルのみとし、リポジトリ関数はこれを必須引数として受け取る。テナントコンテキストなしにクエリを組み立てる経路をコンパイル時に存在させない |
| NF-5-7 | スコープ済みハンドルの `select` / `update` / `delete` ヘルパは、内部で `tenantId` 条件を**必ず AND 結合**する。呼び出し側が渡す `where` はこの条件に追加されるのみで、**上書き・除去はできない**シグネチャとする |

> `forTenant()` に渡す値は NF-5-1 の関数から得る。MVP ではこれが設定値の固定 `TENANT_ID` を返すため、実質的にプロセス起動から終了まで単一のスコープ済みハンドルを使い回す形になる。

## 第2層: 実行前にSQLを検査する 〔MVP対象外・将来必須〕

| ID | 要件 |
|---|---|
| NF-5-8 | **マルチテナント化にあたり、D1 バインディングをラップし実行される SQL を発行直前に検査する。** テナントスコープ対象テーブルを参照する `SELECT` / `UPDATE` / `DELETE` に `tenantId` の述語が含まれていない場合、クエリを実行せず例外を送出する（fail closed） |
| NF-5-9 | NF-5-8 の検査は文字列解析であり完全ではない。**第1層の代替ではなく、第1層をすり抜けた生SQL・手書きクエリを捕捉するための backstop** として位置づける。検査の通過はテナント条件が意味的に正しいことを保証しない |

> **MVP で見送る理由**: MVP は1DBに1テナントしか存在しないため（NF-5-5・NF-5-15）、条件の記述漏れがあっても露出する他テナントのデータが存在しない。本層が防ぐのは MVP では発生し得ない事象である。
> 一方、実装は D1 バインディングのラッパという固有性の高いコードであり、第1層・第3層と比べて費用対効果が MVP 時点では低い。**マルチテナント化の着手時に、テナント条件の実装状況を棚卸しするタイミングで導入する。**

## 第3層: テストで実際に検出する 〔MVP対象〕

| ID | 要件 |
|---|---|
| NF-5-10 | **クロステナント統合テストを MVP から必須とする。** テスト用DBにテナントA・Bの2件と各々のデータを投入し、**アプリケーションをテナントA として起動**（`TENANT_ID=A`）した状態で全ての読み取り系エンドポイントを呼び出し、レスポンスにテナントBのレコードが1件も含まれないことを検証する |
| NF-5-11 | 更新系についても、テナントA として起動した状態でテナントBのレコードIDを指定した操作が失敗し、かつ**対象レコードが変更されていない**ことを検証する |
| NF-5-12 | **エンドポイント一覧と NF-5-10 の検証対象一覧を突き合わせるテストを設ける。** 新規エンドポイントがテストに登録されないまま追加された場合、テストが失敗する。テスト自体の網羅漏れを検出するための措置 |
| NF-5-13 | 名寄せ（F-6）を NF-5-10 の重点対象とする。**氏名照合は全会員を走査するため、条件が抜けた場合の照合相手が必ず他テナントのデータになる。** 本システムで最も危険なクエリである |

> **テナントが設定固定でもこのテストは成立する。** テナントBのデータはアプリケーションを経由せず直接DBへ投入し、アプリケーションはテナントA としてのみ動作させる。検証するのは「A として動くアプリが B のデータに到達しないこと」であり、アプリが複数テナントを扱えることは前提としない。
> **本テストは MVP から必須とする。** MVP に実害がないからといって省略すると、テナント条件が実際には機能していない状態のまま実装が蓄積し、マルチテナント化の時点で全クエリを検証し直すことになる。

## 第4層: 運用上のデータ同居を避ける 〔採用しない〕

| ID | 要件 |
|---|---|
| NF-5-14 | **顧客ごとの環境払い出しは行わない**（[運用要件](./operations.md)）。MVP は単一のデモ環境を全商談で共用する |
| NF-5-15 | **起動時に `Tenant` テーブルの行数が1件であることを検証し、2件以上であれば起動を失敗させる。** MVP はテナント切り替えを持たないため、2件目の存在は誤ったデータ投入か環境の取り違えを意味する。NF-5-10 のテスト環境ではこの検証を無効化する |

> **この層は存在しない。** 要件定義書 v1.3 までは環境分離を「コードの正しさに依存しない最後の防御層」と位置づけていたが、v1.4 でこれを取りやめた。
>
> **帰結**: 将来マルチテナント化した場合、**テナント条件の記述漏れを実害から守る運用上の層は存在せず、第1層（型）と第3層（テスト）だけが防御となる。** マルチテナント化の着手時には、見送っている第2層（SQL検査・NF-5-8）の導入が事実上必須になる。
>
> MVP 自体はテナントが1件のみで実データも投入しない（NF-3-3）ため、この層の欠如による現時点でのリスクはない。

## 個別の注意点 〔MVP対象〕

| ID | 要件 |
|---|---|
| NF-5-16 | **単一レコード取得でテナントが一致しない場合は 404 を返す**（403 ではない）。403 は「そのIDのレコードが存在する」ことを他テナントに開示してしまう |
| NF-5-17 | JOIN を含むクエリでは、**結合する各テーブルに個別に `tenantId` 条件を付与する。** 親テーブルのみの条件に依存しない（親子のテナント不整合が存在した場合に検出できないため） |
| NF-5-18 | 件数・集計・CSV出力（F-8）・ダッシュボードの統計値も対象とする。**表示件数が漏れれば他テナントの規模が推定できる** |
| NF-5-19 | 原本画像の署名付きURL発行前に、対象オブジェクトキーの `{tenantId}/` プレフィックスが現在のテナントと一致することを検証する（NF-2-14・NF-5-21） |
| NF-5-20 | `Member.memberNumber` の採番はテナント単位の連番とする（`MAX + 1` を同一テナント内で算出）。採番処理自体もテナント条件の対象である |
| NF-5-21 | R2オブジェクトキーは `{tenantId}/{applicationId}.{ext}` 形式とする。後からプレフィックスを変更するには実オブジェクトの移動が必要になるため、当初から付与する |
| NF-5-22 | AI Gateway のキャッシュ（AI-2）はテナントを区別しない。同一画像を複数テナントが投入した場合、応答時間の差から**その画像が過去に処理された事実が推測され得る。** OCR結果自体は同一入力に対する同一出力でありDB由来の情報漏洩ではないため、デモにおいては許容する |
