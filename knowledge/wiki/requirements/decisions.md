# 判断記録（要求からの変更点と確定事項）

> 正典化元: 要件定義書 v1.11 §10・§13（原本は `knowledge/ref/doc/claude_code_要件定義_v1.11.md`）
> 対照元の要求ドキュメントは `knowledge/ref/doc/20260814_要求.md`。

## 要求ドキュメントからの変更点

| # | 要求 § | 変更内容 | 理由 |
|---|---|---|---|
| 1 | §5 | Next.js → **Vite + React SPA + Hono** | 無料枠のバンドルサイズ制限。またプロトタイプがSPAのため移植が容易 |
| 2 | §5 | SQLite（ファイル）+ Prisma → **D1 + Drizzle** | Workers に永続FSが無い。Prisma はバンドルが重い |
| 3 | §5 | `/uploads` ローカル保存 → **R2** | 同上 |
| 4 | §4-A | bcrypt / argon2 → **PBKDF2（WebCrypto）** | Workers でネイティブモジュールが使用不可 |
| 5 | §3 | AIモデル `claude-sonnet-4-6` → **Gemini 3.1 Flash Lite** | 日本語手書きOCRのベンチマーク結果（[選定根拠](../architecture/ai-api.md#選定根拠)） |
| 6 | §6 | **`CheckRun` テーブルを新設** | 上書き保存ではAIの判定履歴が失われ監査できない |
| 7 | §6 | `AppStatusHistory.changedById` / `Application.lastEditedBy` をリレーション化 | 他の履歴テーブルとの一貫性 |
| 8 | §6 | `Application.editedCount` に既定値 0 を設定 | 挿入時の指定漏れを防ぐ |
| 9 | §6 | `MatchCandidate` に UNIQUE(applicationId, memberId) を追加 | 再実施時の重複登録防止 |
| 10 | §10 | マルチテナント → **クエリのテナント条件は実装する**（[テナント分離](./tenant-isolation.md)）。**テナントは設定固定の1件**とし、識別・切替は対象外 | 後から全クエリへ条件を追加すると漏れを検出できないため条件は初めから入れる。一方テナント切替はMVPに不要で、供給源を1関数に閉じれば後から差し替えられる |
| 11 | §10 | `orgId` → **`tenantId`** に名称統一 | 同一概念を2つの名前で呼ばない（[用語](./tenant-isolation.md#用語)） |
| 12 | — | **F-9 デモデータのリセットを新設** | 単一環境を全商談で共用するため、商談ごとに初期状態へ戻す手段が必要（[運用要件](./operations.md)・下記 #8） |

> **#7 の `changedById` / `lastEditedBy` は、2026-08-26 の列名統一で `createdById` / `updatedById` へ改名した**（[列名の規約](../db/data-model.md#列名の規約)）。本表は要求ドキュメントとの差分の記録であるため、**行そのものは当時のまま残す。** リレーション化したという判断内容は変わっていない。

## 確定事項

**全20件が確定済み（#1〜14: 2026-08-20、#15: 2026-08-21、#16: 2026-08-26、#17〜18: 2026-08-27、#19: 2026-08-28、#20: 2026-09-01）。仕様上の未確定事項は残っていない。**

以下は要件定義の作成過程で判断を要した項目と、その確定内容である。いずれも MVP（営業デモ）としての判断であり、**製品版への移行時には再検討の対象となる。**

| # | 項目 | 確定した方針 | 該当要件 |
|---|---|---|---|
| 1 | ステータスの逆行 | `差戻し → 審査中` のみ許可。**承認の取り消しは MVP では不要**（`承認` は確定状態） | F-4-2 |
| 2 | 原本画像の保持期間 | **30日**で自動削除 | NF-3-1 |
| 3 | CSVインポートの重複判定 | **インサートのみ。既存会員の更新は行わない。** 会員番号一致でスキップ | F-8-7 |
| 4 | CSVインポートの件数上限 | **500件／回** | F-8-6 |
| 5 | 項目ラベルの正規化 | **行わない**（AI出力をそのまま列名に使用） | F-8-4 |
| 6 | 同時編集の排他 | **行わない**（後着優先） | F-4-12 |
| 7 | 確信度の閾値 | **85%**。定数として保持し、環境変数化は行わない | NF-4-3 |
| 8 | デモデータのリセット機能 | **F-9 として実装する。** シード会員は削除も更新もしない。値の復元処理は実装しない | [F-9](./functional.md#f-9-デモデータのリセットadmin-のみ) |
| 9 | 独自ドメイン | **MVP は `*.workers.dev` を使用する。** 独自ドメインは取得しない | OP-12 |
| 10 | OCR実行上限 | **セッション単位では設けず、月次で制限する。月間読取120枚（`MAX_OCR_PAGES_PER_MONTH`）／月間Gemini呼び出し720回（`MAX_GEMINI_CALLS_PER_MONTH`）／業務チェック再実施は1申請あたり5回（`MAX_CHECK_RUNS_PER_APPLICATION`）。** いずれも環境変数で変更可能（コードへハードコードしない）。判定は専用の `UsageCounter` テーブルで行い、**F-9 のリセットでは枠が戻らない** | NF-2-18〜22・NF-2-34〜41 |
| 11 | マルチテナント化時のログイン方式 | **MVP では実装しない**（`TENANT_ID` 固定のため不要）。方式の選定はマルチテナント化の着手時に行う | [テナント分離](./tenant-isolation.md#ログイン画面のテナントコード入力) |
| 12 | 旧字体・異体字対応表 | **MVP はJSONファイルで定義しGit管理する。DB・実行時CSV・AI APIは使用しない。** 原文を保持して正規化値を別カラムに保存する。動的・テナント別編集や大規模化が必要になった場合にDB化を再検討する | F-6-1・2・11〜13、NF-4-4 |
| 13 | 公開デモの前段認証 | **静的アセット・SPA・全APIをBasic認証で保護し、その後もアプリ内ログインを必須とする。** 資格情報はWorkers Secretへ保存し、Static AssetsはWorker先行で認証を通す | F-1-11〜15、NF-2-23〜28、OP-13 |
| 14 | OCR構成のリリース順 | **MVP 1.0はGemini単体、MVP 1.1はDocument AI Enterprise Document OCRを前段に追加してOCR文字・レイアウト＋元画像をGeminiへ渡す。** 画面・API・最終JSONは共通とし、1.1でもGeminiが項目抽出と業務チェックを担う | F-2-11〜15、NF-4-2・5〜7、[外部OCR・AI API](../architecture/ai-api.md) |
| 15 | AI Gatewayの利用範囲 | **経由させるがログのペイロード収集は無効化する**（既定ONのままでは帳票の元画像がCloudflareへ保存される）。**メタデータ収集は維持**しコスト計測に使う。**Guardrailsは使用せず**（Workers AIのトークン推論として課金される）、**Workers AI課金は「標準課金」を選択する**（統合課金はクレジットに5%の手数料）。予算上限は公開ベータのため最終防衛線と位置づけ、一次的な歯止めはアプリ側の月次上限とする | NF-2-15・NF-2-42〜45、AI-7a〜9a |
| 16 | データモデルの列名と更新の記録 | **同一の役割には同一の列名を使う**（#11 と同じ理由）。`processedById` / `lastEditedById` / `executedById` / `executedAt` / `changedById` / `registeredAt` を `createdAt` / `updatedAt` / `createdById` / `updatedById` へ統一する。**`StaffUser` と `Member` に更新の記録を追加する**（F-7 のスタッフ管理と F-5 の会員編集は人手で運用するが、誰がいつ変更したかを残す手段が無かった）。**追記専用のテーブルには `updatedAt` / `updatedById` を付けない。** `MatchCandidate.decidedById` / `decidedAt` は F-6-9 の業務データであり改名しない。**閲覧の記録は対象外** | [データモデル §列名の規約・監査列](../db/data-model.md#列名の規約) |
| 17 | 状態値の永続化 | **状態・AI判定は英字文字列コードを TEXT として永続化し、日本語は画面・CSVの表示ラベルに限定する。** 値集合は TypeScript の型と SQLite/D1 の `CHECK` 制約で二重に制限する。遷移可否はサービス層で検証する | [データモデル §状態値の永続化](../db/data-model.md#状態値の永続化) |
| 18 | 原本画像の一時配信 | **Workerがアプリ内認可とR2キーのテナントprefix検証後、R2 S3互換APIのGET署名URLを都度発行する。** URLは15分で失効し、DB・localStorage・ログへ保存しない。再表示時または失効時は `GET /api/images/:applicationId` で新しいURLを取得する。発行用のAccess Key IDとSecret Access KeyはWorkers Secret、Account IDは通常の環境変数とする | NF-2-14・NF-5-19・[API画像取得](../architecture/api.md#原本画像) |
| 19 | 無料枠内のログと例外処理 | **Workers Logsを使用し、外部I/O境界をtry/catch/finallyで管理する。正常時はInvocation Logだけ、429・500・503等の失敗時は安全な構造化ログを最上位で1件だけ出す。** 下位層は失敗位置を付加して必ず再throwし、認証情報・個人情報・帳票・AIペイロード・SQL値は記録しない。1リクエスト最大2イベントとして、Freeの10万リクエスト/日と20万ログイベント/日を両立する | [ログ・例外処理・可観測性設計](../architecture/observability.md) |
| 20 | AI GatewayエンドポイントURLの構成情報 | **CloudflareアカウントIDとゲートウェイ名を環境変数 `AI_GATEWAY_ACCOUNT_ID` / `AI_GATEWAY_ID` として新設する。** 原本・要件定義には無いエンドポイント構築の実装詳細であり、既存の `R2_ACCOUNT_ID`（R2 S3 API専用）とは用途が異なるため流用しない。いずれも未設定時は起動を失敗させる | NF-2-46、[外部OCR・AI API](../architecture/ai-api.md#外部呼び出し) |

## 撤回した判断

要件定義の過程で一度採用し、後に取り下げた論拠。**同じ結論を再導出しようとした際に、成立しない前提を再利用しないための記録である。**

| 撤回した記述 | 撤回した時期 | 理由 |
|---|---|---|
| 顧客ごとに環境を払い出し、環境分離を「コードの正しさに依存しない最後の防御層」とする（第4層） | v1.4 | MVP はデモとしてのみ使用し、顧客へ環境を引き渡さないため。分離すべき顧客データが存在しない。帰結として[第4層は存在しない](./tenant-isolation.md#第4層-運用上のデータ同居を避ける-採用しない) |
| `UNIQUE(tenantId, memberNumber)` は「今しか設定できない」（複数環境の統合時に `memberNumber` が全件衝突するため） | v1.4 | 上記により統合すべき別環境が存在しなくなった。制約自体は妥当だが緊急性はない（[スキーマ側を今確定させる理由](./tenant-isolation.md#スキーマ側を今確定させる理由)） |
| リセット時にシード会員の値を復元する処理が必要（承認操作で `status` が `pending → active` に変わるため） | v1.4 | プロトタイプ `SEED_MEMBERS` を確認したところ**シード会員は5件とも `status: "active"` で投入されており**、F-4-3 の `pending` 条件が発火しない。加えて商談で会員管理を提示しない方針が確定した（[復元しない根拠](./functional.md#シード会員の値を復元しない根拠)） |
| `orgId` という列名（要求ドキュメント由来） | v1.3 | 同一概念を2つの名前で定義すると識別できなくなるため `tenantId` に統一 |
