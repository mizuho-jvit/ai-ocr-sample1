# プロジェクト概要とスコープ

> 正典化元: 要件定義書 v1.11 §1・§2・§3・§12（原本は `knowledge/ref/doc/claude_code_要件定義_v1.11.md`）

## 目的

自治体・企業では手書き申請書を職員が手動で Excel や基幹システムへ転記しており、多大な工数が発生している。本システムは、生成AIベースのOCRによりこの転記作業を置き換えることを訴求する**営業デモ用アプリケーション**である。題材は「施設（図書館等）の利用者登録申請」を想定する。

本システムは**実運用システムではなく、商談における提案ツール**である。この前提が、[性能要件・セキュリティ要件](./non-functional.md)の水準を規定する。

## プロダクトポジショニング（設計・UI文言の制約）

以下は営業戦略に直結するため、**機能追加・改修時も必ず維持すること**。

1. **「文字を読むOCR」ではなく「一次審査まで行うAI」として位置づける。** 従来型OCRとの読取精度勝負を避け、審査業務の代替という土俵で訴求する。
2. **「全自動」ではなく「人間は疑わしい箇所だけ確認する」ワークフローとして提示する。** AIへの警戒感が強い自治体層への予防線として、以下の趣旨の注記を画面上に常時表示する。
   - 「最終判断は必ず職員が行う」
   - 「AIが申請者へ直接連絡することはない」
3. **AIの確信度（confidence）は自己申告値であり統計的な精度保証ではない**旨を「目安」として注記する。

## デザイン要件

「日本の公文書」の世界観を維持する。

| 要素 | 指定 |
|---|---|
| 見出し | 明朝体 |
| アクセントカラー | 朱色 `#BE3B2B` |
| 判定表示 | 判子風の円形スタンプ |
| 基調色 | 紙色 `#F6F5F0` / 墨色 `#1C2233` |

プロトタイプ `ai-ocr-demo.jsx`（`knowledge/ref/doc/`）冒頭のカラーパレット定数群をそのまま踏襲する。

## スコープ

### 対象範囲

| # | 機能 | 概要 |
|---|---|---|
| F-1 | 職員認証 | admin / staff のログイン、ロール制御 |
| F-2 | 帳票読取（OCR） | 画像アップロード、AIによる帳票種別判別・項目抽出 |
| F-3 | AI業務チェック | 整合性検証、不備検出、トリアージ判定、差戻し文面生成 |
| F-4 | 申請管理 | 申請一覧・詳細、ステータス遷移、項目編集、業務チェック再実施 |
| F-5 | 会員管理 | 会員CRUD、検索、状態遷移、申請履歴表示 |
| F-6 | 名寄せ | 2段階（ルールベース絞り込み＋AI最終判定）による重複検出 |
| F-7 | スタッフ管理 | admin によるスタッフアカウント管理 |
| F-8 | CSV入出力 | 台帳エクスポート、会員名簿インポート／エクスポート |
| F-9 | デモデータのリセット | 申請・原本画像・履歴を削除し、デモ開始前の状態へ戻す（admin のみ） |

各機能の詳細は [機能要件](./functional.md)。

### MVPバージョン別のOCR構成

| 製品版 | OCR構成 | スコープ |
|---|---|---|
| **MVP 1.0** | 画像 → Gemini 3.1 Flash Lite | 本線。Geminiが帳票種別判別、項目抽出、確信度付与を行う |
| **MVP 1.1** | 画像 → Document AI Enterprise Document OCR → OCR文字・レイアウト＋元画像 → Gemini 3.1 Flash Lite | 1.0の画面・API・保存形式を維持したまま、Pass①の前段OCRを追加する |

- MVP 1.1でも最終JSON生成とPass②の業務チェックはGeminiが担当し、Document AI単独で項目抽出を完結させない。
- 利用者が画面から方式を選択する機能は設けず、デプロイ環境の `OCR_PIPELINE_MODE` で固定する。
- MVP 1.1はMVP 1.0の完成後に着手し、1.0の受け入れ基準を回帰試験する。

### 対象外（実装しない）

- 会員（一般ユーザー）のログイン・マイページ・オンライン申請機能
- 施設予約・設備利用・書籍貸出の機能本体（会員 `status` による利用資格の有無のモデル化までとする）
- 審査ルールの管理画面からの編集（設計上ハードコード依存を避けるのみ）
- メールの自動送信（差戻し文面は下書き生成までが仕様）
- 基幹システム連携
- **テナントの識別・管理・切り替え機能**（テナント管理画面、ログイン後のテナント選択、セルフサインアップ、セッションからのテナント解決）。**扱うテナントは設定ファイル（環境変数 `TENANT_ID`）で固定した1件のみ**とする。ただし**全クエリへのテナント条件付与は MVP から実装する**（[テナント分離](./tenant-isolation.md)）
- 記入ミス統計・様式改善レポート

## ユーザーとロール

システムにログインするのは**管理者とスタッフのみ**である。一般ユーザー（申請者）はログインせず、**会員データとしてシステム内に存在するだけ**とする。

| 種類 | ログイン | 役割 |
|---|---|---|
| 管理者（admin） | あり | 申請書の読取・審査・台帳確定／スタッフ管理／会員管理 |
| スタッフ（staff） | あり | 申請書の読取・審査・台帳確定／会員管理 |
| 会員（一般ユーザー） | **なし（データのみ）** | 申請者。承認により利用資格が付与される |

### 権限マトリクス

| 操作 | admin | staff |
|---|:---:|:---:|
| 申請書のOCR読取・業務チェック・台帳確定 | ✓ | ✓ |
| 名寄せ候補の判断（紐付け／別人／保留） | ✓ | ✓ |
| 会員の登録・編集・状態変更・無効化 | ✓ | ✓ |
| 申請状況の管理（一覧・状態変更） | ✓ | ✓ |
| スタッフアカウントの登録・編集・無効化 | ✓ | — |
| デモデータのリセット（F-9） | ✓ | — |

権限はフロントエンドの表示制御だけでなく、**APIレベルで必ず検証する**こと。

### 会員のライフサイクル

```
[紙の申請書] → OCR読取 → 職員による確認・業務チェック → 台帳確定
   ├─ 名寄せで既存会員と紐付け → 既存会員の申請履歴に追加
   └─ 新規 → 会員データとして登録

会員 status: pending（申請受付） → active（承認・利用資格あり）
                                 → suspended / inactive（停止・退会）
```

状態変更はすべて職員が管理画面から行う。差戻し候補の場合は `pending` のままとし、差戻し文面の下書きを生成する（送付は職員が手動で行い、システムからの自動送信は行わない）。

## 制約事項・前提条件

| # | 内容 |
|---|---|
| 1 | 本システムは営業デモ用であり、実運用に耐えるセキュリティ強度・可用性を持たない |
| 2 | パスワードハッシュの強度をデモ環境で意図的に低減している（NF-2-7） |
| 3 | 顧客の実データ（実在の個人情報）を投入しない運用を前提とする |
| 3-2 | **単一のデモ環境を全商談で共用する**（[運用要件](./operations.md)）。投入したデータは他の顧客の目に触れ得る。商談の前後に F-9 のリセットを実行する運用を前提とする |
| 4 | Cloudflare 無料枠の範囲内で構築する。有料プランへの移行は行わない |
| 5 | AI APIのみ従量課金が発生する（デモ規模では月数百円程度の想定） |
| 6 | 確信度（confidence）はAIの自己申告値であり、統計的な精度保証ではない |
| 7 | 1申請＝1画像とし、複数枚・両面帳票には対応しない |
