# 機能要件 F-1〜F-9

> 正典化元: 要件定義書 v1.11 §5（原本は `knowledge/ref/doc/claude_code_要件定義_v1.11.md`）
> 前提となるスコープ・ロールは [プロジェクト概要とスコープ](./overview.md)。

## F-1 職員認証

| ID | 要件 |
|---|---|
| F-1-1 | メールアドレス＋パスワードによる認証を行う |
| F-1-2 | パスワードは PBKDF2-SHA256（WebCrypto）でハッシュ化して保存する。詳細は [非機能要件（セキュリティ）](./non-functional.md#セキュリティ) |
| F-1-3 | セッションは HTTPOnly / Secure / SameSite=Lax の Cookie で管理する。**JWT を localStorage に保存してはならない** |
| F-1-4 | セッション情報は D1 に保存し、サーバー側で失効させられること |
| F-1-5 | ロールによる画面・APIアクセス制御を行う。API レベルで必ず検証する |
| F-1-6 | ログイン失敗が連続5回に達した場合、当該アカウントを15分間ロックする。カウンタは D1 に保持する |
| F-1-7 | ログインエラーの文言は成否要因を問わず「メールまたはパスワードが違います」に統一する（アカウント存在の推測を防ぐ） |
| F-1-8 | 未ログイン時は全画面をログイン画面へリダイレクトする |
| F-1-9 | デモ用シードアカウントとして admin 1件・staff 1件を投入し、認証情報を README に記載する |
| F-1-10 | ログアウト機能を提供し、サーバー側のセッションを破棄する |
| F-1-11 | **デモ環境への前段ゲートとしてHTTP Basic認証を設ける。** 静的アセット、SPAの全画面、全APIを対象とし、未認証リクエストには `401` と `WWW-Authenticate` を返す |
| F-1-12 | Basic認証に成功した後も、従来のアプリ内ログインを必須とする。Basic認証は職員識別・セッション・admin / staff のロール認可を代替しない |
| F-1-13 | Basic認証にはHonoのBasic Auth Middlewareを使用し、APIハンドラおよびStatic Assets配信より前に適用する |
| F-1-14 | Basic認証のユーザー名・パスワードはアプリ内シードアカウントと異なる値とし、README・ソースコード・ログへ記載しない |
| F-1-15 | Basic認証のパスワードはパスワードマネージャー等で生成した20文字以上のランダム値とし、漏えいが疑われる場合はSecretを差し替える |

> ログイン画面にテナントコードの入力欄は設けない。理由は [テナント分離](./tenant-isolation.md#ログイン画面のテナントコード入力)。

## F-2 帳票読取（OCR）

| ID | 要件 |
|---|---|
| F-2-1 | 画像のアップロードに対応する（カメラ撮影・ファイル選択・ドラッグ＆ドロップ） |
| F-2-2 | クライアント側で長辺1568px・JPEG品質85%にリサイズしてから送信する |
| F-2-3 | **1申請＝1画像**とする。複数枚・両面の帳票は対象外 |
| F-2-4 | AIにより帳票種別を自動判別する（例:「利用者登録申請書」） |
| F-2-5 | 申請者記入欄の項目をラベル・値のペアで抽出する。空欄の項目も値を空文字として含める |
| F-2-6 | 各項目に確信度（0〜1）を付与する |
| F-2-7 | 「使用欄」「事務局記入欄」「受理番号」等の職員記入欄は抽出対象から除外する |
| F-2-8 | **読取完了と同時に申請レコードを保存する**（ステータス「受付」）。以降の操作を中断しても申請一覧に残り、後から再確認・編集が可能であること |
| F-2-9 | 原本画像を R2 に保存し、申請レコードに紐付ける（監査証跡） |
| F-2-10 | 処理中は段階的な進捗表示を行う（外部OCR・AI APIの待機を許容させるため） |
| F-2-11 | **MVP 1.0では、前処理済み画像をGemini 3.1 Flash Liteへ直接入力し、帳票種別・項目・確信度を共通JSONスキーマで取得する** |
| F-2-12 | **MVP 1.1では、前処理済み画像をDocument AI Enterprise Document OCRへ入力し、そのOCR文字・レイアウト情報と同じ元画像をGeminiへ入力する。** Geminiが最終的な帳票種別・項目・確信度を共通JSONスキーマで生成する |
| F-2-13 | MVP 1.0と1.1で、画面、`POST /api/ocr/extract` の入出力、申請の保存形式を変更しない。方式差はサーバー内部のOCR Pipelineに閉じ込める |
| F-2-14 | MVP 1.1でDocument AIが失敗した場合、Gemini単体へ自動フォールバックしない。読取失敗として再試行可能なエラーを返し、構成不良や精度差を隠さない |
| F-2-15 | Document AIの生レスポンスおよび全文OCRテキストは永続化しない。最終的にGeminiが生成した抽出項目と既存仕様の原本画像のみを保存する |

> 月間の読取枚数には上限がある（`MAX_OCR_PAGES_PER_MONTH`）。[非機能要件（AI呼び出し回数の上限）](./non-functional.md#ai呼び出し回数の上限アプリケーション側)を参照。

## F-3 AI業務チェック

読取結果に対し、2回目のAI呼び出しで以下を実施する。

| ID | 要件 |
|---|---|
| F-3-1 | **整合性検証**: 項目間の論理矛盾を検出する（郵便番号↔住所、氏名↔カナ、日付の妥当性）。重要度は error（明確な矛盾）／warning（疑わしい）で区分する |
| F-3-2 | **不備検出**: 必須項目の記入漏れを検出する。任意項目の空欄は不備として扱わない |
| F-3-3 | **名寄せ照合**: F-6 の方式で既存会員との重複を検出する。抽出項目からどのラベルで氏名・氏名カナ・生年月日・電話番号を拾うかは[決定#26](./decisions.md) |
| F-3-4 | **トリアージ判定**: 「承認候補」「要審査」「差戻し候補」のいずれかと、1〜2文の理由を出力する |
| F-3-5 | **差戻し文面生成**: 不備または矛盾がある場合のみ、申請者向け連絡文の下書きを生成する。敬体・200字以内、宛名と差出人はプレースホルダとする。職員が編集・コピー可能であること |
| F-3-6 | 審査ルールは定数として定義するが、**将来の管理画面編集を見据えハードコードに依存しない構造とする** |
| F-3-7 | 業務チェックの実行結果は履歴として保存する（[`CheckRun`](../db/data-model.md#checkrun--業務チェック実行結果)）。最新結果を申請レコードから参照する |

## F-4 申請管理

### F-4-1 申請ステータス

職員の決裁状態を表す `appStatus` と、AI判定を表す `triage` は**別軸で保持する**。AI判定は参考情報であり、決裁状態を自動的に変更しない。

```
受付 ──────→ 審査中 ──┬──→ 承認
（読取完了時    （業務チェック  │
  に自動作成）    確定時）      └──→ 差戻し
```

| ID | 要件 |
|---|---|
| F-4-2 | ステータス遷移は上図に加え、`差戻し → 審査中` の再開を許可する。`承認` からの遷移は不可（確定状態とする） |
| F-4-3 | `承認` へ変更した際、紐付く会員が `pending` であれば自動的に `active` へ昇格させ、会員状態遷移履歴に記録する |
| F-4-4 | すべてのステータス変更を履歴に記録する（変更者・日時・前後の状態・備考） |
| F-4-5 | 申請詳細画面で原本画像と抽出項目を再表示し、項目の編集が可能であること。編集者を記録する |
| F-4-6 | **業務チェックの再実施**: ステータスが `受付` / `審査中` / `差戻し` の申請に対し、現在の抽出データ（編集内容を含む）で再実施できる。`承認` 済みの申請では実施不可。**再実施回数は1申請あたり `MAX_CHECK_RUNS_PER_APPLICATION` 回まで**（NF-2-21） |
| F-4-7 | 再実施時、`受付` の申請は自動的に `審査中` へ遷移する |
| F-4-8 | 再実施結果は新たな `CheckRun` として記録し、履歴に「業務チェック再実施（AI判定: X）」を残す |
| F-4-9 | 再実施で得られた名寄せ候補からも会員への紐付けが可能であること |
| F-4-10 | **申請一覧**: AI判定・処理状態・処理者・会員紐付け有無でフィルタできること |
| F-4-11 | 「要審査のみ」を表示するビューを提供する（職員の日常動線の想定） |
| F-4-12 | 同時編集の排他制御は行わない（後着優先）。デモ用途のため |

> F-4-3 は F-9（リセット）の設計判断の前提になっている。シード会員が5件とも `active` で投入されるため、デモ動線では発火しない。[F-9 のシード会員の扱い](#シード会員の値を復元しない根拠)を参照。

## F-5 会員管理

| ID | 要件 |
|---|---|
| F-5-1 | 会員の一覧・検索・登録・編集・状態変更・無効化を提供する |
| F-5-2 | 保持項目: 会員番号（自動採番）／氏名／氏名カナ／生年月日／郵便番号／住所／電話番号／メール（任意）／登録日／状態 |
| F-5-3 | 状態は pending（申請中）／active（利用資格あり）／suspended（停止中）／inactive（退会）の4種とする |
| F-5-4 | 検索条件: 氏名・カナの部分一致、生年月日、電話番号、状態フィルタ |
| F-5-5 | **表記ゆれ検索**: F-6-1 の正規化処理を検索キーにも適用し、「渡辺」で「渡邊」がヒットすること |
| F-5-6 | 会員詳細画面に申請履歴（原本画像へのリンク付き）と状態遷移履歴を表示する |
| F-5-7 | 会員状態の手動変更が可能であること。変更者・日時・理由を記録する |
| F-5-8 | 会員の物理削除は行わない。無効化（inactive）のみとする |
| F-5-9 | **重複疑いリスト**: 未解決の名寄せ候補を一覧表示するビューを提供する |
| F-5-10 | デモ用シードデータとして会員5件を投入する。プロトタイプの `SEED_MEMBERS` を踏襲し、旧字体の「仙臺 一郎」を含めること（デモ再現性の確保） |

> **商談では会員管理を提示しない方針**（OCR読取〜承認の動線のみを見せる）。この方針が F-9 でシード会員の値を復元しない根拠になっている。

## F-6 名寄せ

会員全件を照合対象としつつ効率よく絞り込むため、**2段階方式**とする。**両段ともAIを使用しない決定的ロジックであり、既存会員の個人情報をAIへ送信しない**（[決定#27](./decisions.md)）。

### 第1段: ルールベースの候補絞り込み（決定的・高速）

| ID | 要件 |
|---|---|
| F-6-1 | 以下の正規化処理を**決定的なアプリケーションロジック**として実装する<br>・旧字体／異体字の統一（仙臺→仙台、髙→高、邊/邉→辺、齋/齊→斎 等）<br>・全角／半角、スペース有無の統一（NFKC正規化）<br>・ひらがな→カタカナの統一（**氏名カナのみに適用し、氏名フィールドには適用しない**。[決定#25](./decisions.md)）<br>・生年月日フォーマットの統一（和暦→西暦を含む。変換規則・改元当日の月日境界は[決定#23](./decisions.md)）<br>・電話番号のハイフン除去 |
| F-6-2 | 表示・出力に使用する原文は変更せず、正規化済みの値を検索・候補抽出用の別カラムとして会員テーブルに保存し、インデックスを付与する |
| F-6-3 | スコアリングにより候補を抽出する（重みは[決定#22](./decisions.md)）<br>・カナ完全一致 ＋ 生年月日一致 → 高スコア<br>・電話番号一致 → 高スコア<br>・正規化後氏名一致 → 中スコア（住所は一致条件に含めない。[決定#21](./decisions.md)） |
| F-6-4 | 上位5件を候補として抽出する |
| F-6-11 | **MVP の旧字体・異体字対応表は JSON ファイルで定義し、Git で版管理する。** DBテーブルおよび実行時に読み込むCSVは作成しない。対応表は全テナント共通とし、管理画面からの編集・即時反映は対象外とする |
| F-6-12 | F-6-1〜4 の正規化・候補抽出、および候補の可能性判定（F-6-5）を含め、名寄せ全体で **AI APIを呼び出さず、AIトークンを消費しない**（[決定#27](./decisions.md)） |
| F-6-13 | JSON対応表に登録されていない文字は変更せず、そのまま正規化結果へ残す |

### 第2段: ルールベースの可能性判定

| ID | 要件 |
|---|---|
| F-6-5 | 絞り込んだ候補それぞれについて、第1段のスコア内訳（カナ完全一致＋生年月日一致・電話番号一致・正規化後氏名一致）から**決定的なロジックで**「同一人物の可能性: 高／中／低」と理由を算出する。**既存会員の氏名・カナ・生年月日・電話番号をAIへ送信しない**（[決定#27](./decisions.md)） |
| F-6-6 | **会員の個人情報（氏名・カナ・生年月日・電話番号等）をAIに渡す方式は採用しない**（会員全件はもちろん、絞り込んだ候補についても渡さない） |

### 判断UI

| ID | 要件 |
|---|---|
| F-6-7 | 業務チェック結果画面に候補カードを表示し、申請データと会員データの項目を左右に並べて差分をハイライトする |
| F-6-8 | 職員の操作として「同一人物として紐付け」「別人として登録」「保留」を提供する |
| F-6-9 | 判断結果・判断者・日時を保存する |
| F-6-10 | 一度 `rejected`（別人）と判断された組み合わせは、業務チェックを再実施しても候補として再提示しない |

> **名寄せはテナント分離の最重点対象である。** 氏名照合は全会員を走査するため、テナント条件が抜けた場合の照合相手が必ず他テナントのデータになる（NF-5-13）。[テナント分離](./tenant-isolation.md#第3層-テストで実際に検出する-mvp対象)を参照。

|---|---|

## F-9 デモデータのリセット（admin のみ）

単一環境を全商談で共用するため（[運用要件](./operations.md)）、商談ごとにデモ開始前の状態へ戻す手段を設ける。

### 対象範囲

| ID | 要件 |
|---|---|
| F-9-1 | **削除する**: `Application`（申請）、`CheckRun`（業務チェック履歴）、`MatchCandidate`（名寄せ候補）、`AppStatusHistory`（申請ステータス履歴）、および R2 上の原本画像 |
| F-9-2 | **シード会員（`Member.isSeed = true`）は削除も更新もしない。** 行をそのまま残す |
| F-9-3 | **デモ中に作成された会員（`isSeed = false`）は削除する。** 併せて当該会員の `StatusHistory` も削除する |
| F-9-4 | `StatusHistory` はシード会員の分も含めて全削除する |
| F-9-5 | **削除しない**: `StaffUser`（職員アカウント）、`Tenant`、`Session`、`UsageCounter`。**実行者はログインしたまま作業を継続できる**。`UsageCounter` を残すのは、リセットで月次のAI呼び出し上限を回避できないようにするため（NF-2-40） |

> **職員アカウントを対象外とする理由**: リセット後にログインし直せなくなる事態を避けるため。デモ中に追加したスタッフは残るが実害がなく、必要であればスタッフ管理画面（F-7）から個別に削除できる。

### シード会員の値を復元しない根拠

**本デモの動線（OCR読取 → 業務チェック → 名寄せ → 承認）では、シード会員の行は一切変化しない。** したがって削除しない（F-9-2）だけで初期状態が保たれ、値を戻す処理は不要である。

シード会員が変化し得るのは会員管理機能（F-5）を操作した場合のみで、**商談ではこれを提示しない方針**のため発生しない。

| カラム | 変更し得る契機 | デモ動線での発生 |
|---|---|---|
| `status` | F-5-7（状態の手動変更）、F-5-8（無効化） | **なし**（提示しない） |
| `name` / `nameKana` / `birthDate` / `postalCode` / `address` / `phone` / `email` | F-5-1（会員の編集） | **なし**（提示しない） |
| `nameNormalized` / `kanaNormalized` | 上記編集に連動して再計算（F-6-2） | **なし** |

`id` / `tenantId` / `memberNumber` / `createdAt`（画面の「登録日」）/ `isSeed` はいずれの操作でも変化しない。

**自動的に変化する経路は存在しない。** F-4-3（承認時に会員を `pending` → `active` へ昇格）は対象が `pending` の会員に限られるが、**シード会員は5件とも `active` で投入される**ため（F-5-10・プロトタイプ `SEED_MEMBERS`）発火しない。名寄せによる紐付け（F-6-8）は `Application.memberId` を設定する操作であり、`Member` 自体を変更しない。

> **この判断が無効になる条件**（いずれかに該当した時点で復元処理の追加を検討すること）
>
> - **シードに `status = pending` の会員を追加した場合** — F-4-3 により、承認操作だけで自動的に `active` へ変わる。**デモ動線のみでも乖離が発生するようになる**
> - 商談で会員の編集・状態変更（F-5-1・F-5-7・F-5-8）を提示する方針に変えた場合
>
> 復元を追加する場合のコストは小さい。シード定義を用いた upsert（`INSERT ... ON CONFLICT(id) DO UPDATE`）1回で済み、専用のロジックを別途書く必要がない。

### 実行手順と安全策

不可逆な全件削除であり、操作を誤ると商談中のデモデータが失われる。以下を必須とする。

| ID | 要件 |
|---|---|
| F-9-6 | **admin のみ実行可能。** フロントエンドの表示制御だけでなく API レベルで検証する（NF-2-11 と同様） |
| F-9-7 | **確認語の入力を求める。** ボタン1つで実行できてはならない。削除対象の件数（申請・画像・会員）を事前に表示したうえで確認させる |
| F-9-8 | 環境変数 `ALLOW_DATA_RESET=true` が設定されていない場合、**機能自体を無効とし、APIは 404 を返す**（機能の存在を露出させない）。実案件へ移行した環境で誤って実行されることを防ぐ |
| F-9-9 | 実行結果として削除件数（申請・画像・会員）を画面に表示する。**併せて「当月のAI呼び出し上限は回復しない」旨を表示する**（NF-2-40。データが消えたことで枠が戻ったと誤解させないため） |
| F-9-10 | 実行の事実（実行者・日時・削除件数）をログに出力する。**削除対象のテーブルには記録しない**（次回のリセットで自ら消えるため記録の意味がない） |

### 実行順序

| ID | 要件 |
|---|---|
| F-9-11 | **① 削除対象の `imageKey` を収集 → ② D1 のレコードを削除 → ③ R2 のオブジェクトを削除** の順で実行する |
| F-9-12 | R2 の削除は prefix `{tenantId}/` の列挙により行う。1リクエストあたりのキー数上限（1000件）に応じて分割する |
| F-9-13 | D1 の削除は外部キーの依存順（子テーブルから）に行う。件数が多い場合はバッチに分割する |

> **この順序である理由**: R2 を先に削除すると、その後 D1 の削除に失敗した場合に**画像を失った申請レコードが残り、申請詳細画面が壊れる。** 逆順であれば、失敗時に残るのは参照されない R2 オブジェクトのみで、画面上の実害がない。R2 と D1 は同一トランザクションで扱えないため、失敗時にどちらが残る方が安全かで順序を決める。
