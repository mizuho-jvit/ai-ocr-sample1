# 本番化ギャップ（未回答の問い・デモ限定の割り切り）

> **正典化元を持たないページである。** 他の `requirements/` 配下は要件定義書 v1.10 の各章を正典化したものだが、本ページは 2026-08-21 の検討で新たに整理した内容であり、要件定義書に対応する章が存在しない。
>
> **本ページの「問い」は MVP の未確定事項ではない。** MVP の要件は v1.10 で確定済み・未確定事項なしである（[要件・仕様の目次](./index.md)）。ここに挙げるのは**本番化を検討する段階で初めて必要になる問い**であり、MVP の実装を止めるものではない。

## このページの目的

**本番のシステム構成を今決めないための記録である。**

本番の要件（規模、テナント数、保存年限、予算、可用性）がまだ存在しないため、現時点で本番構成を描いても推測にとどまる。それを Wiki に置くと、後から「決定事項」として引用され、成立しない前提を再利用する事故につながる（[判断記録](./decisions.md)の「撤回した判断」と同じ構造の問題）。

したがって本ページは構成案を持たない。代わりに次の3点を保持する。

1. **[本番化までに答えが必要な問い](#本番化までに答えが必要な問い)** — 答えによって構成の選択が変わるもの
2. **[デモ限定の割り切りと本番での代替方針](#デモ限定の割り切りと本番での代替方針)** — 現在 Wiki 各所に散在しているものの集約
3. **[既に本番を見据えて手当て済みの箇所](#既に本番を見据えて手当て済みの箇所)** — 重複して作り直さないための記録

## 本番化までに答えが必要な問い

| ID | 問い | この答えで変わる設計判断 |
|---|---|---|
| **Q-1** | **業務データ（個人情報）の保存場所に所在地の要件があるか。** 国内保存の縛り、越境移転の同意取得、委託先の監督義務 | **構成の選択そのもの。** D1・R2 の配置可能なリージョン、そもそも Cloudflare を使えるか |
| **Q-2** | **調達側がクラウドサービスの登録制度（ISMAP 等）への適合を要求するか** | 同上。使用可能なサービスの母集団が確定する |
| Q-3 | 1顧客専用の環境を払い出すのか、複数顧客を1インスタンスに載せるのか | マルチテナント化の要否。載せる場合は第2層 SQL検査（NF-5-8）が必須になる |
| Q-4 | 月間の申請件数、同時利用者数、繁忙期のピーク | D1 の容量・実行環境の CPU 制約が成立するか。AI 呼び出しの月次上限値 |
| Q-5 | 業務データと原本画像の保存年限。監査への提出要件があるか | 現在の「原本画像30日で削除」（NF-3-1）の妥当性。バックアップ方針 |
| Q-6 | 職員認証を既存の ID 基盤（SSO / IdP）に委譲するか、自前で持つか | 自前 PBKDF2 の継続可否。`StaffUser` の識別子設計（メールアドレスを鍵にするか外部 subject を持つか） |
| Q-7 | 可用性の要求水準。AI API が停止したとき業務を止めてよいか | 縮退運転の要否。AI を経由しない手入力経路を用意するか |
| Q-8 | 複数枚・両面の帳票を扱うか | `OcrPipeline` の入力型と1申請あたりのコスト構造（現在は1申請＝1画像・制約7） |

### Q-1・Q-2 を優先する理由

Q-3 以降は「後から直せる」問いだが、Q-1・Q-2 は**外れた場合に構成ごと作り直しになる**点で性質が異なる。

理由はデモの前提そのものにある。MVP は実在の個人情報を投入しない運用が前提であり（NF-3-3・制約3）、Cloudflare 無料枠の範囲で構築する（制約4）。つまり**現在の構成は、本番を規定するはずの制約に一度も当たっていない。** 当たっていない制約は、当たった時点で設計の外側から効いてくる。

想定顧客が自治体・公共系である場合（`Tenant.code` の例が `sendai-city`、[将来拡張](../db/data-model.md#将来拡張)が施設予約・図書貸出であることから示唆される）、調達要件にクラウドサービスの制度適合が入る可能性がある。**ただしこれは推測であり、まず顧客側の調達要件を確認する必要がある。** Wiki には現時点で顧客の調達要件に関する一次情報が存在しない。

Q-1・Q-2 は設計作業ではなく**確認事項**であるため、着手コストは小さい。答えが「制約なし」であれば本番も現構成の延長で伸ばせる。「国内限定」または「制度適合が必要」であれば、デモの段階からベンダ非依存の度合いを上げる判断が入る。**この分岐を早く知ることに価値がある。**

## デモ限定の割り切りと本番での代替方針

**現在 Wiki 各所に散在している「デモ用の妥協」の集約である。** 分散していると、読み手が「どれがデモ限定でどれが本設計か」を区別できない。

| # | 項目 | デモでの割り切り | 本番での代替方針 | 出典 |
|---:|---|---|---|---|
| 1 | 投入データ | 実在の個人情報を投入しない | **本番は実データ前提。** Q-1・Q-2 の回答が前提条件になる | NF-3-3・制約3 |
| 2 | パスワードハッシュ | PBKDF2 20,000回。`ALLOW_WEAK_PASSWORD_HASH=true` で明示的に許可。**暗号強度は本番水準にない** | 100,000回以上へ引き上げ、または Q-6 により IdP へ委譲。CPU時間制約が外れる実行環境なら素直に引き上げ可 | NF-2-7・制約2 |
| 3 | 前段ゲート | Basic認証で静的アセット・SPA・全APIを保護 | デモ環境を外部から隠すための措置であり本番では不要。撤去時は `run_worker_first = true` の前提も併せて見直す | F-1・[システム構成](../architecture/cloudflare-stack.md#全体構成) |
| 4 | 会員側の認証 | ログイン手段・認証情報が一切存在しない（職員が代行入力する） | 会員セルフサービスを設けるなら認証基盤と `Member` の識別子設計から検討（Q-6） | F-1・[受け入れ基準](./acceptance.md#認証認可) |
| 5 | テナント | `TENANT_ID` で1件に固定。2件目を投入すると起動失敗 | NF-5-1 の関数をセッション参照へ差し替える。**同時に第2層 SQL検査の導入が必須**（#6） | NF-5-1・NF-5-15 |
| 6 | SQL検査層 | 見送る。第4層（環境払い出し）も行わないため、**型とテストだけが防御** | マルチテナント化の着手時に事実上必須 | NF-5-8・[テナント分離](./tenant-isolation.md#第2層-実行前にsqlを検査する-mvp対象外将来必須) |
| 7 | 環境の分離 | 単一のデモ環境を全商談で共用する。投入データは他顧客の目に触れ得る | Q-3 により、顧客ごとの環境払い出しか論理分離かを決める | NF-5-14・制約3-2・OP-9 |
| 8 | Google Cloud 認証 | サービスアカウント秘密鍵を Workers Secret に保持 | Workload Identity Federation 等の短期資格情報へ切り替える | [外部AI API](../architecture/ai-api.md#設定と認証) |
| 9 | AI呼び出し上限 | 月120枚・Gemini 720回・1申請5回 | 本番規模で再設定する。**環境変数の書き換えと再デプロイのみで完結する**（NF-2-36） | NF-2-18・NF-2-34・NF-2-21 |
| 10 | デモデータリセット | F-9 でデータを一括削除できる。`ALLOW_DATA_RESET` 未設定なら画面非表示・API 404 | **本番環境では絶対に有効化しない。** 設定未投入で機能自体が存在しなくなる現在の構造を維持する | F-9-8 |
| 11 | 原本画像の保持 | 30日で削除 | Q-5 の保存年限次第。併せてバックアップ方針を決める | NF-3-1 |
| 12 | インフラの上限 | Cloudflare 無料枠（CPU 10ms／リクエスト、100,000リクエスト／日、D1 5GB、R2 10GB） | Q-4 次第。**CPU 10ms 制約が外れると #2 と画像のクライアント側リサイズ（F-2-2）の根拠が消える**ため、両方を再検討する | [実行環境の制約と対応](../architecture/cloudflare-stack.md#実行環境の制約と対応) |
| 13 | 帳票の形式 | 1申請＝1画像。複数枚・両面に非対応 | Q-8 次第。`OcrPipeline` の入力型と1申請あたりのコスト構造に影響する | 制約7 |

## 既に本番を見据えて手当て済みの箇所

**本番化で最も高くつく類の設計は、MVP の時点で既に入っている。** 重複して作り直さないための記録である。

| 項目 | 状態 | 根拠 |
|---|---|---|
| マルチテナント対応スキーマ | 全テーブルに `tenantId`、`UNIQUE` の複合キー化、R2キーの `{tenantId}/` プレフィックス、全 SELECT / UPDATE / DELETE のテナント条件まで実装対象 | [テナント分離の方針](./tenant-isolation.md#方針) |
| テナント供給源の一点化 | `tenantId` を返す関数を1つだけ定義し、**マルチテナント化時はこの関数の実装のみを差し替える。** リポジトリ層・ハンドラは変更しない | NF-5-1・NF-5-2 |
| R2キーの設計 | 後からプレフィックスを変更すると実オブジェクトの移動が必要になるため、当初から付与する | NF-5-21 |
| 会員番号・メールアドレスの一意性 | `UNIQUE(tenantId, memberNumber)` / `UNIQUE(tenantId, email)`。単独 `UNIQUE` にすると将来のテナント統合時に全件衝突する | [データモデル](../db/data-model.md#member--会員ログインなし) |
| テナントコード列 | `Tenant.code` を使用しないまま列だけ用意済み。ログイン時のテナント指定に使える | [データモデル](../db/data-model.md#tenant--テナント顧客組織) |
| OCRベンダの差し替え | `OcrPipeline` 境界により `/api/ocr/extract` はプロバイダ固有コードを持たない | [OCR Pipeline境界](../architecture/ai-api.md#ocr-pipeline境界) |
| モデルの差し替え | `GEMINI_MODEL` で設定。コードへハードコードしない | [採用モデル](../architecture/ai-api.md#採用モデル) |
| 上限値の変更 | 環境変数で定義し、ハードコード・スキーマ変更・データ移行を伴わない | NF-2-36 |
| 審査ルールの変更 | 定数として定義するが、将来の管理画面編集を見据えハードコードに依存しない構造とする | F-3-6 |

## 要件として未記載のギャップ

**本番では要求される見込みが高いが、現在どのページにも要件が存在しないもの。** MVP で実装する必要はないが、後付けのコストが高い順に記録する。

| # | ギャップ | 後付けが高くつく理由 |
|---:|---|---|
| 1 | **個人情報の閲覧監査ログ**（誰がどの会員・申請を閲覧したか） | 現在 `AppStatusHistory` / `StatusHistory` は状態の**変更**を記録するが、**閲覧を記録するテーブルは存在しない。** 後から追加すると全ての読み取り経路に手を入れることになる。要件を1行置いておくだけでも設計時に効く |
| 2 | データ主体の権利への対応（開示・訂正・利用停止の請求への導線） | 対象データの横断的な特定と出力が必要。データモデルとエクスポート機能の両方に影響する |
| 3 | バックアップとリストアの手順 | 現在 D1 のバックアップ方針が[運用要件](./operations.md)に存在しない。保存年限（Q-5）と対で決める |
| 4 | AI API 停止時の縮退運転 | 現在は再試行可能なエラーを返す設計のみ。AI を経由しない手入力経路を用意するかは業務要件（Q-7） |
| 5 | 権限の粒度 | 現在は admin / staff の2ロール。本番で部署単位・案件単位の制限が必要になると権限モデルの再設計になる |

## 進め方

1. **Q-1・Q-2 を顧客・上長へ確認する**（設計作業ではなく確認事項）
2. 回答が出た時点で Q-3〜Q-8 を埋める
3. **そこで初めて本番構成を検討する。** 本ページに構成案を追記するのではなく、`architecture/` 配下に別ページを起こす
4. 本番化に着手した時点で、[デモ限定の割り切り](#デモ限定の割り切りと本番での代替方針)の各行を移行チェックリストとして使う
