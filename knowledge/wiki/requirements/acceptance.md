# 受け入れ基準

> 正典化元: 要件定義書 v1.11 §14（原本は `knowledge/ref/doc/claude_code_要件定義_v1.11.md`）
> 各項目の根拠となる要件は [機能要件](./functional.md)・[非機能要件](./non-functional.md)・[テナント分離](./tenant-isolation.md)。

## 認証・認可

- [ ] Basic認証なし、または資格情報が誤っている場合、`/`、静的アセット、全APIが `401` と `WWW-Authenticate` を返す
- [ ] Basic認証に成功するとアプリ内ログイン画面が表示されるが、アプリ内ログイン前は業務APIへアクセスできない
- [ ] `BASIC_AUTH_USERNAME` / `BASIC_AUTH_PASSWORD` のいずれかが未設定の場合、アプリケーションが起動しない
- [ ] Basic認証の資格情報がフロントエンドバンドル、README、Git追跡ファイル、ログ、エラー応答に含まれない
- [ ] Workers Static AssetsがBasic認証を迂回せず、`run_worker_first = true` でWorkerの認証処理を通る
- [ ] 未ログインでは全画面・全APIにアクセスできない（API直接呼び出しでも 401）
- [ ] admin はスタッフ登録ができ、staff はできない（API直接呼び出しでも 403）
- [ ] 会員側にログイン手段・認証情報が一切存在しない
- [ ] ログイン失敗5回でアカウントがロックされる
- [ ] `PBKDF2_ITERATIONS` 未設定時、アプリケーションが起動しない
- [ ] デモ環境で `PBKDF2_ITERATIONS=20000` と `ALLOW_WEAK_PASSWORD_HASH=true` を設定すると起動し、シードアカウントでログインできる
- [ ] `PBKDF2_ITERATIONS` が 100,000 未満かつ `ALLOW_WEAK_PASSWORD_HASH` 未設定時、アプリケーションが起動しない
- [ ] `PBKDF2_ITERATIONS` の値を変更しても、既存アカウントでログインできる

## OCR・業務チェック

- [ ] MVP 1.0で `OCR_PIPELINE_MODE=gemini` を設定すると、Document AIを呼び出さず、画像をGeminiへ直接渡して共通JSONを取得する
- [ ] MVP 1.1で `OCR_PIPELINE_MODE=document-ai-gemini` を設定すると、Document AIのOCR文字・レイアウトと元画像をGeminiへ渡して共通JSONを取得する
- [ ] MVP 1.0と1.1で、`POST /api/ocr/extract` の入出力、画面、申請の保存形式が同一である
- [ ] `OCR_PIPELINE_MODE` 未設定または未知の値でアプリケーションが起動しない
- [ ] MVP 1.1でDocument AI固有設定のいずれかが未設定の場合、アプリケーションが起動しない。MVP 1.0ではその設定を要求しない
- [ ] MVP 1.1でDocument AIが失敗した場合、Gemini単体へ自動フォールバックせず、再試行可能なエラーを返す
- [ ] Document AIの生レスポンス、OCR全文、OAuthアクセストークン、サービスアカウント秘密鍵がログ・D1・R2へ保存されない
- [ ] 読取完了と同時に申請レコードが「受付」で保存され、以降を中断しても申請一覧に残る
- [ ] 確信度85%未満の項目が黄色でハイライトされる（閾値は定数。NF-4-3）
- [ ] **同一セッションで帳票を連続して読み取れる**（セッション単位の制限がないこと。NF-2-22）
- [ ] `MAX_OCR_PAGES_PER_MONTH` に達すると読取が実行されず、上限到達のメッセージが表示される（NF-2-18・NF-2-20）
- [ ] `MAX_OCR_PAGES_PER_MONTH` / `MAX_GEMINI_CALLS_PER_MONTH` / `MAX_CHECK_RUNS_PER_APPLICATION` 未設定時、アプリケーションが起動しない（NF-2-18・NF-2-34・NF-2-21）
- [ ] 上限値に 0・負値・非数値・小数を設定した場合、アプリケーションが起動しない（NF-2-35）
- [ ] ホーム画面に当月の残り読取可能枚数が表示される
- [ ] **F-9 のリセット実行後も当月のカウンタは初期化されず、読取可能枚数が戻らない**（NF-2-40）
- [ ] `UsageCounter.period` が前月のまま残っている状態で読取を実行すると、当月の期間キーで 0 から計上される（NF-2-19）
- [ ] 上限値を現在の消費量より小さい値へ引き下げた場合、当月は即座に上限到達として扱われる（NF-2-37）
- [ ] 上限値をクエリパラメータ・ヘッダ・画面操作で上書きできない（NF-2-38）
- [ ] 業務チェックの再実施が `MAX_CHECK_RUNS_PER_APPLICATION` 回で拒否される（NF-2-21）
- [ ] 全項目が直接修正可能で、修正が記録される
- [ ] 読取の応答時間がMVP 1.0で15秒以内、MVP 1.1で20秒以内である
- [ ] 業務チェックを再実施でき、実行ごとに `CheckRun` が記録される
- [ ] 「承認」済みの申請では業務チェックを再実施できない

## 名寄せ

- [ ] サンプル申請書（仙台一郎）を処理すると、シード会員「仙臺 一郎」が**ルールベース段階で**候補に抽出され、AI判定「高」が付く
- [ ] 「同一人物として紐付け」により `Application.memberId` が設定され、会員詳細の申請履歴に表示される
- [ ] 「別人として登録」と判断した候補が、業務チェック再実施後に再提示されない
- [ ] 会員検索で「渡辺」を入力すると「渡邊」がヒットする
- [ ] 「仙臺」と「仙台」、「髙」と「高」、「邊／邉」と「辺」がそれぞれ同じ検索キーへ正規化される
- [ ] 正規化後も `Member.name` の原文が書き換わらず、`Member.nameNormalized` に検索用の値が保存される
- [ ] JSON対応表に登録されていない文字が削除・置換されず、そのまま正規化結果に残る
- [ ] ルールベースの正規化・候補抽出ではAI APIが呼び出されず、AIトークンを消費しない

## 申請・会員管理

- [ ] 新規承認の申請から会員が作成され、status が active になる。変更が StatusHistory に記録される
- [ ] 申請状況一覧で「要審査」だけを絞り込める
- [ ] すべてのステータス変更に変更者と日時が記録される

## 出力・セキュリティ

- [ ] CSV出力に AI判定・判定理由・処理者名 が含まれ、Excelで文字化けしない
- [ ] AI APIキーがフロントエンドのバンドル・ネットワークタブに一切露出しない
- [ ] 原本画像が署名付きURL経由でのみ取得でき、URLが期限切れする
- [ ] AI Gateway に予算上限が設定されている（NF-2-15）
- [ ] **予算上限に到達すると AI 呼び出しが実行されずエラーになる**（超過して処理が継続しない。NF-2-16）
- [ ] **デモを1件実行した後、AI Gateway のログに元画像・リクエスト本文・レスポンス本文が保存されていない**（NF-2-42・NF-2-32）
- [ ] 同じログにトークン数・モデル・費用・所要時間のメタデータが記録されている（NF-2-43。ペイロードだけを止めていること）
- [ ] ゲートウェイの設定で Guardrails が無効である（NF-2-44）
- [ ] ゲートウェイの「Workers AI 課金」が「標準課金」になっている（NF-2-45）
- [ ] デモを1件実行した後、Cloudflare ダッシュボードの Workers AI 使用量（neurons）が増えていない（BYOKでのプロキシがWorkers AI課金を発生させないことの実測確認）

## テナント分離

**検証はテナントを2件投入した状態で行う。** 1テナントのみの環境では、条件の有無で結果が変わらないため分離の欠陥を検出できない。

スキーマ:

- [ ] 全テーブルに `tenantId` が存在し、NOT NULL である
- [ ] 同一メールアドレスの職員を異なる `tenantId` で2件登録できる（`UNIQUE(tenantId, email)`）
- [ ] 同一の会員番号を異なる `tenantId` で2件登録できる（`UNIQUE(tenantId, memberNumber)`）
- [ ] R2に保存された原本画像のキーが `{tenantId}/` で始まる

設定と起動時検証:

- [ ] `TENANT_ID` 未設定でアプリケーションが起動しない（NF-5-4）
- [ ] `TENANT_ID` に `Tenant` テーブルに存在しない値を設定すると起動しない（NF-5-5）
- [ ] `Tenant` テーブルに2件目を投入すると起動しない（NF-5-15）
- [ ] リポジトリ層・ハンドラのコードに `TENANT_ID` の直接参照が存在しない（NF-5-2）
- [ ] リクエストのヘッダ・ボディ・クエリ文字列に `tenantId` を与えても無視される（NF-5-3）

分離の実効性（**テナント2件を投入し、`TENANT_ID=A` で起動して検証する**）:

- [ ] **全ての読み取り系エンドポイント**の応答に、テナントBのレコードが1件も含まれない（NF-5-10）
- [ ] テナントBの申請ID・会員IDを指定した取得が **404** を返す（403 ではない。NF-5-16）
- [ ] テナントBのレコードを更新・削除できず、対象レコードが変更されていない（NF-5-11）
- [ ] 会員検索・名寄せ候補抽出（F-6）にテナントBの会員が出現しない（NF-5-13）
- [ ] 申請一覧・ダッシュボードの件数、CSV出力の行数にテナントBのレコードが算入されない（NF-5-18）
- [ ] テナントBの原本画像に対する署名付きURLが発行されない（NF-5-19）
- [ ] テストに登録されていないエンドポイントを追加すると、突き合わせテストが失敗する（NF-5-12）

**MVP対象外**（マルチテナント化時に実施）:

- [ ] SQL検査ラッパ（NF-5-8・9） — MVP では実装しない
- [ ] セッションからのテナント解決（NF-5-1 の差し替え） — MVP では設定固定
- [ ] ログイン画面のテナントコード入力欄 — MVP では設けない（`Tenant.code` 列のみ用意）

## デモデータのリセット（F-9）

- [ ] admin のみ実行でき、staff は実行できない（API直接呼び出しでも 403。F-9-6）
- [ ] `ALLOW_DATA_RESET` 未設定の環境では、画面にメニューが表示されず API も **404** を返す（F-9-8）
- [ ] 確認語を入力しない限り実行されない。事前に削除対象の件数が表示される（F-9-7）
- [ ] **事前に件数を表示した後、実行までの間に削除対象（申請・非seed会員）が増減した場合、削除は実行されず409が返る**（F-9-7・[決定#51](./decisions.md)）
- [ ] 実行後、申請・業務チェック履歴・名寄せ候補・申請ステータス履歴が0件になる（F-9-1）
- [ ] 実行後、R2 に原本画像が残っていない（F-9-1）
- [ ] **実行後もログインが維持され、職員アカウントが削除されていない**（F-9-5）
- [ ] **実行後も `UsageCounter` が削除・初期化されていない**（F-9-5・NF-2-40）
- [ ] 実行結果として削除件数が表示され、**併せて「当月のAI呼び出し上限は回復しない」旨が表示される**（F-9-9）

シード会員の保全（**デモ動線を2周以上繰り返して確認する**）:

- [ ] 実行後もシード会員5件が存在し、`id` / `memberNumber` / `status` / 各項目がリセット前と一致する（F-9-2）
- [ ] デモ中に登録した会員（`isSeed = false`）のみが削除されている（F-9-3）
- [ ] **デモ動線（読取 → 業務チェック → 名寄せで紐付け → 承認）を一巡してもシード会員の行が変化しない**（[復元しない根拠](./functional.md#シード会員の値を復元しない根拠)の前提確認）
- [ ] リセット直後にサンプル申請書を処理すると、名寄せでシード会員「仙臺 一郎」が再び候補に出る（初期状態への復帰確認）
- [ ] **上記がリセット2回目・3回目でも同様に成立する**（状態の累積的な乖離がないこと）

## データモデル（[列名の規約・監査列](../db/data-model.md#列名の規約)）

- [ ] 全テーブルに `processedById` / `lastEditedById` / `executedById` / `executedAt` / `changedById` / `registeredAt` が存在しない（列名統一の完了確認）
- [ ] スタッフアカウントを編集すると `StaffUser.updatedAt` と `updatedById` が更新され、**`role` を `staff → admin` に変更した操作の実行者が特定できる**
- [ ] スタッフアカウントを `isActive = false` にした操作の実行者と日時が特定できる
- [ ] F-9 のリセットを実行しても `StaffUser` の監査列が失われない（F-9-5 で削除対象外のため）
- [ ] 会員の住所・電話・氏名を編集すると `Member.updatedAt` と `updatedById` が更新される（`StatusHistory` には残らない変更であること）
- [ ] CSVインポート（F-8-5）で登録された会員の `createdById` にインポート実行者が記録される
- [ ] 会員一覧・会員詳細に表示される「登録日」が `Member.createdAt` の値である（F-5-2 の保持項目が失われていない）
- [ ] 業務チェックを再実施すると `MatchCandidate.updatedAt` が更新され、**先に行った採否判断の `decidedById` / `decidedAt` は変化しない**
- [ ] `CheckRun` / `AppStatusHistory` / `StatusHistory` に `updatedAt` / `updatedById` が存在しない（追記専用であること）
- [ ] 監査列がAPI応答に含まれない（[api.md](../architecture/api.md) と [types.md](../architecture/types.md) に定めのない列を返していない）
- [ ] シード投入で作成された会員・職員の `createdById` が `NULL` である（アプリケーション外の操作を表す）
- [ ] 画面から作成したレコードの `createdById` が `NULL` にならない
- [ ] レコード作成直後の `updatedAt` が `NULL` ではなく `createdAt` と同値である
- [ ] `createdById` / `updatedById` が指す `StaffUser` が同一テナントに限られる（テナントBの職員IDが混入しない）

## プロダクト要件

- [ ] 「最終判断は担当者が行う」系の注記文言がプロトタイプから失われていない
- [ ] 確信度が「目安」である旨の注記が表示されている
- [ ] カラーパレット・明朝体見出し・判子風スタンプが維持されている
