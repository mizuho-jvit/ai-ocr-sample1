### Scope decision: Task 001 vs Task 002

Task 001 now owns the shared safety contract and enforces its invariant before any concrete repository exists. The concrete Drizzle/D1 executor, repository functions, tenant-row existence/count startup checks, and seed data remain correctly deferred to Task 002, whose Goal, Interfaces, Test Strategy, and Files explicitly assign those behaviors there.

This split satisfies the dependency direction: Task 002 can implement `TenantScopedExecutor` and use `createForTenant()` while application-facing repositories receive only `ScopedDb`. No raw D1/Drizzle handle is introduced by Task 001.

## Tenant Boundary Verification

The following properties were confirmed from source and tests:

1. `TenantScopedTable` excludes the global `usage_counter` table.
2. `select`, `selectOne`, `update`, and `delete` always delegate with `{ operator: "and", tenant, additional }`.
3. The wrapper and tenant predicate are frozen, so caller code cannot replace the enforced scope after construction.
4. A conflicting caller predicate such as `tenantId = tenant-b` remains an additional predicate and cannot replace `tenantId = tenant-a`.
5. Insert values cannot declare `tenantId` through the public type and the scoped ID is injected at runtime.
6. Update values cannot declare `tenantId` through the public type and a cast-injected value is removed at runtime.
7. Empty tenant scopes fail closed.
8. `createForTenant()` provides Task 002 with a `tenantId => ScopedDb` factory.
